# Lab 1 implemented contract — Mădălina

This addendum describes **tamagotchi-user-management-service:0.1.1** and **tamagotchi-map-service:0.1.1**. They implement the Lab 0 [User Management API](../README.md#user-management-api) and [Map API](../README.md#map-api) under the [team Lab 1 conventions](lab-1-conventions.md). Paths, `snake_case` field names, status codes and schemas are those of the Lab 0 contract. This page records only what Lab 1 adds, pins down or interprets. Owners of affected services, please review the sections that concern you: Guild, Battle, Monster Raid and Package Registry call User Management; Notification consumes both services' events.

## Common wire rules (both services)

- **Public routes** (`/api/v1`): with `AUTH_MODE=mock` (the Lab 1 setting) the caller is the UUID in `X-Mock-User-Id`. A missing or non-UUID header returns `401`. User Management also accepts `Authorization: Bearer <access token>` issued by itself, in both modes. With `AUTH_MODE=jwt` only bearer tokens are accepted: User Management verifies its own, and Map validates them against User Management's JWKS. `X-Mock-Roles` is not used, because neither service has admin-only routes.
- **Internal routes** (`/internal/v1`, User Management only): with `AUTH_MODE=mock` the caller is named in `X-Service-Name`, otherwise `401`. The caller must be listed for the route, otherwise `403 SERVICE_NOT_ALLOWED`. A trusted package backend identifies itself as `package:<package_id>`. With `AUTH_MODE=jwt` the caller sends `Authorization: Bearer <service token>` from `INTERNAL_SERVICE_TOKENS` instead. Outgoing calls send both `X-Service-Name` and, when configured, the bearer token.
- **Idempotency** (stricter than the Lab 1 default in the conventions, as the Lab 0 contract requires): mutating routes require `Idempotency-Key: <UUID>`. A missing key is `400 IDEMPOTENCY_KEY_REQUIRED` and a non-UUID key is `400 INVALID_IDEMPOTENCY_KEY`. The same key with the same body within 24 hours returns the stored success response; the same key with a different body is `409 IDEMPOTENCY_KEY_REUSED`. Failed requests are not stored, so they can be retried with the same key. Exempt routes: login, refresh and logout (their responses would store plaintext refresh tokens) and the read-only `POST /internal/v1/users/batch`.
- **Errors:** `{code, message, request_id, details: {field, reason}[]}`. Malformed JSON is `400 MALFORMED_JSON`. Invalid field values, unknown fields (for example `is_admin` on registration) and malformed path IDs are `422` with the field named in `details`. Every response carries `X-Request-Id`: the caller's value when it is a UUID, otherwise a new one; error bodies repeat it as `request_id`.
- **Pagination:** `limit` (1–100, default 20) and an opaque `cursor`, returning `{items, next_cursor}` ordered by `created_at`, then ID. A cursor from another caller or query is `422 INVALID_CURSOR`.
- **Dependencies:** outgoing calls time out after 2 s and retry twice with backoff. An unavailable dependency is `503 DEPENDENCY_UNAVAILABLE` with `Retry-After: 5`; nothing is guessed or written without the check.
- **Health, storage, events:** `GET /health` returns `200 {"status":"ok"}` after a database round trip (`503` if the database is down). Storage is PostgreSQL only; Map also uses PostGIS. Prisma migrations run in the container entrypoint when `RUN_MIGRATIONS=true`, and `DATABASE_URL` is built from `DB_*`. Events are written to a transactional outbox in the same transaction as the change. With `EVENT_PUBLISHER=log` (Lab 1) the relay logs the `Event<T>` envelope; `rabbitmq` publishes it to `tamagotchi.events.v1` with publisher confirms.

## User Management (port 8085)

All endpoints in the Lab 0 table are implemented, including real RS256 login, refresh, logout and JWKS.

| Lab 1 behaviour | Contract impact |
| --- | --- |
| **New:** `POST /internal/v1/users/batch`, callers `guild`, `package-registry`, `battle`, `map`. Body `{user_ids: Id[]}` with 1–500 IDs; returns `200 {users: User[]}` in request order, omitting unknown IDs. Read-only, so no `Idempotency-Key`. | Addition to the Lab 0 table. Map needs it to fill `LocatedUser.user` for up to 500 users in one call. |
| Access tokens: RS256, `iss = user-management`, `aud = tamagotchi-go`, `sub = user_id`, 15-minute expiry, `jti`, and `kid` set to the key's RFC 7638 thumbprint. The key comes from `JWT_PRIVATE_KEY_PATH`, or an ephemeral key is generated at startup. | Pins the claims every service must check in the integration lab. With an ephemeral key, tokens stop working after a restart. |
| Refresh tokens: 32 random bytes (base64url), stored only as SHA-256, valid 7 days, rotated atomically. A reused or revoked token is `401 INVALID_REFRESH_TOKEN`. Logout always returns `204`. | As in Lab 0, with the error code fixed. |
| Registration: `username` 3–32 characters from `A–Z a–z 0–9 _ . -`, unique case-insensitively; `email` stored lower-cased and unique; `password` 8–128 characters; `display_name` 1–64. Conflicts are `409 USERNAME_TAKEN` / `EMAIL_TAKEN`. The global wallet is created with the account, at 0. | Field limits the Lab 0 table left open. |
| Friendships: a user who is not a party gets `404` (IDs are not revealed); the requester accepting gets `403 NOT_RECIPIENT`; accepting an accepted friendship returns it unchanged. Other errors: `422 SELF_FRIENDSHIP`, `409 FRIENDSHIP_EXISTS` (either direction), `409 ENEMY_MARKED`. | Error codes and the idempotent acceptance are additions. |
| Enemy markers: `PUT` is idempotent and `DELETE` always returns `204`. Other errors: `422 SELF_ENEMY`, `409 ACCEPTED_FRIENDSHIP`. | As in Lab 0, with the error codes fixed. |
| Settlements: battle operations only from `battle` and raid operations only from `monster-raid`, otherwise `403 SETTLEMENT_SOURCE_FORBIDDEN`. Rule violations are `422 SETTLEMENT_RULES_VIOLATION` with one detail per field. For raids, `422 UNKNOWN_RAID_DEFINITION` / `REWARD_MISMATCH` against the pinned definition. `422 UNKNOWN_USER` for unknown participants. | The Lab 0 rules, enforced as written. |
| Settlement idempotency: the same `operation_id` and body returns the stored `WalletResult`; the same `operation_id` with another body is `409 OPERATION_CONFLICT`; a second settlement of the same battle or raid is `409 SOURCE_ALREADY_SETTLED`. Zero-amount entries are omitted, so a loser with balance 0 produces no debit entry. | Callers can retry safely with the same body. |
| Local operations: the caller must be `package:<package_id>` for the package in the body, otherwise `403 PACKAGE_NOT_BOUND`. `delta` must not be 0. An unregistered user is `422 USER_NOT_REGISTERED`; an overdraft is `409 INSUFFICIENT_FUNDS`. The local wallet is created on first use. | The Lab 0 binding rule, with the error codes fixed. |
| Seed (`SEED_ON_START=true`, users table empty): Alice, Bob, Carol and admin (password `password123`), the Alice–Bob friendship, Carol's enemy marker on Bob, and starting balances recorded as ledger operation `…00f1`. Reference copy: [`db/seed/user-management-service.json`](../db/seed/user-management-service.json). | Uses the shared IDs from the conventions. |
| Package Registry mock (`USE_MOCKS=true`): registrations are Alice in A and B, Bob in A, Carol in B, anyone else none. Raid definition Big Slime `…00d1` version 1 exists with `currency_reward = 30`; other definitions return not found (`422` on settlement). The monster fields are placeholders and not used by User Management. | Replaced by the real Package Registry in the integration lab; Big Slime's reward must then come from Registry data. |

## Map (port 8086)

`PUT`, `GET` and `DELETE` are implemented as in Lab 0: 6 m proximity, re-arming beyond 10 m or after a stale gap, 120 s freshness, 30 s future tolerance, 60 s cooldown, at most 500 users.

| Lab 1 behaviour | Contract impact |
| --- | --- |
| **Directional enemies:** a pair counts as unrelated, and can produce `UsersNearby`, only when neither user has the other as a friend or enemy. `relationship` in `GET /map/users` is from the caller's own point of view. | Settles the open Lab 0 question. Map reads both users' `Relationships`, but only for candidates within 6 m. |
| No relationship cache: Map asks User Management on every request, so friend and enemy changes apply at once. Profiles come from one `POST /internal/v1/users/batch` call. Users unknown to User Management are left out of `GET /map/users`. | Depends on the new batch endpoint above. |
| Encounters are detected **after** the location commits. The pair moves to `near` through one conditional upsert, and only the request that performs that transition writes the `UsersNearby` outbox row. If two users enter range at the same moment, exactly one event is emitted and none is lost. | Stronger than the Lab 0 wording ("no duplicates"): no missed encounters either. |
| With User Management down, `GET /map/users`, and a `PUT` that has candidates within 6 m, return `503` with `Retry-After`. The location of that `PUT` is already stored. A retry returns `accepted: false` (same timestamp) and runs encounter detection again. | The `503` on `PUT` does not mean the location was dropped. |
| Validation: `accuracy_m` is positive and at most 100 000. `recorded_at` is RFC 3339; values outside the time window are `422 INVALID_RECORDED_AT`. `distance_m` is rounded to centimetres. `DELETE` keeps each pair's cooldown timestamp. | Limits the Lab 0 table left open. |
| `UsersNearby`: `user_ids` sorted, `correlation_id = encounter_id`, `producer = map`, routing key `users.nearby`. | As in Lab 0. |
| No seed: locations are live data that expire after 120 s. | `SEED_ON_START` is accepted and does nothing. |
| User Management mock (`USE_MOCKS=true`): Alice–Bob friends, Carol → Bob enemy, profiles `alice`, `bob`, `carol`, `admin`. Any other UUID is a user named `user_<first 8 hex>` with no relationships. | Replaced by the real User Management in the integration lab (`USE_MOCKS=false`, `USER_MANAGEMENT_URL`). |

## Team integration status

Both images are public on Docker Hub and run in the common Compose file as `user-management-service` and `map-service` on the shared `postgres`; they can also run standalone from their private repositories. The Postman collections `postman/user-management-service.postman_collection.json` (28 requests) and `postman/map-service.postman_collection.json` (12 requests) cover every endpoint above. They pass with Newman on repeated runs, and the Lab 1 smoke workflow runs both against the full stack.
